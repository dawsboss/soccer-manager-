# CLAUDE.md

**TeamPlayHQ** (teamplayhq.com; called *Minutes* until build 132; `APP_NAME` in `app.js` is the one place the app reads its name from in code, the rest is copy). Soccer minutes/substitution tracker, the team's season calendar, and each person's own calendar across teams. Static site (`app.js`, `index.html`, `styles.css`; `live.js` behind the share pages; `ics.js`, the calendar-file writer both load), Firebase Realtime Database backend, deployed to GitHub Pages. Server-side code is allowed (the owner's decision, 2026-10-06): Cloud Functions on the same Firebase project, in `functions/`. Build 104 shipped the first three: push for notices and family messages (with `sw.js` and `manifest.webmanifest` on the site for them), and the calendar feed, which was a Cloudflare Worker until then. Built for a coach tracking subs on a phone at the sideline, often with no signal.

## Required after every change to app.js or index.html

- **`node test/run.js`** — runs every suite below in its own process and exits non-zero if any fails. This is the one to remember; four separate commands is how one of them quietly stops being run. `node test/run.js --verbose` shows everything, and `node test/run.js sync clock` runs just those.
- Don't skip it because a change looks small. It's under a second, and it's what catches a regression before it costs someone a Saturday.

## Required after every change to the rules (`database.rules.json`)

- **One ruleset, for every club: `database.rules.json`** (`firebase.json` points the Firebase CLI at it). A database runs one set of rules for every club in it and this site is for any club that turns up, so there is no open "starter" set and no lockdown: a brand-new club is made under the same rules as an established one, by the server (`functions/join.js`, `joinAsk`: admin, owner and index in one write at a code it issues); the bootstrap clauses (claim admin and index yourself while the code has neither) survive for codes starting `test-` alone, the app owner's test clubs seeded on a phone. Never add a second ruleset; `rules.js` fails if one appears. README explains them and points at them, but never carries a whole copy — a second copy is the one that drifts, and `rules.js` fails if one reappears. Edit the file, never a pasted-back block.
- **Edit `database.rules.json` itself.** While clubs moved to `orgs/{code}` the rules were built from a source by a script; the old tree and the build came out in build 128 (rules version 26, AUTH.md build order step 5). Every lookup into a club says `root.child('orgs/' + $code + ...)`, and `workspaces/` has no rule.
- **Every change to the rules raises their version**: the number in `rulesVersion`'s `.write`, and `RULES_VERSION` in `app.js` to match, then `node test/rules.js --stamp` to record it in `test/rules-stamp.json`. `rules.js` fails on a change without a bump, so an admin's phone (`checkRules()`, pinned by `test/rulesver.js`) and `node tools/live-rules.js` can tell whether the club has pasted it. Before telling the owner the rules still need pasting, run `node tools/live-rules.js`; don't infer it from the docs.
- `node test/rules.js` — evaluates `database.rules.json`, the file you paste, against a mock club, for every kind of account, and walks a brand-new club from nothing to working under the same rules. Every club in the mock is laid out on `orgs/{code}` (paths translated as `clubPath()` does), and it checks who reads each part (the squad, members, names, roster, log), the squad kept out of `teams/`, the old tree closed to everyone, and the root rules following a club there. Exits non-zero on a failed expectation. Rules are the one thing here with no way to try it safely: the only live test is publishing over the real club, and the failure mode README warns about is silent (reads work, every write is refused). Run it before you paste anything into the Firebase console.

## Invariants — do not violate these

- **A club lives on `orgs/{code}`, and nowhere else** (AUTH.md, *The move to `orgs/{orgId}`*; SECURITY.md, SEC-1). On `orgs/` nothing grants the club whole: each part has its own readers (the squad at `squad/{tid}` to its staff, every coach and the admins, a child's record also to her own family and herself; the coach's `note`, `rating`, `pairs` and `avoid` on a child not on her record but at `coachNotes/{tid}/{pid}`, to coaches and admins only, sent there by `clubWrites()` a field at a time and laid back onto the player in memory, never written whole for a team; `members/` to admins and coaches; `log` to admins; teams, games, answers, `roster/`, `names/`, `org` and `access` to everyone in the club). The app keeps the old shape in memory (a team with its players, access with org, members and log), reads a club a part at a time (`wireOrgs()`), and sends every write through one translation (`clubPath()`, `clubWrites()`): never build a club path any other way. Writes wait in the outbox until a session's first read of the club has answered (`fb.held`). `roster/` and `names/` are derived (the server keeps them; the phone writes a roster beside a squad change, `rosterAfter()`, and staff their own name, `staffName()`); never put a child's name there except the roster's while the club opens it. The old `workspaces/{code}` tree came out of the rules, the server and the app in build 128 (AUTH.md, build order step 5): never read, write or add a rule for it again. A phone's copy made from the old tree is cut down once before the club is read (`copyFromOrgs()`, `forgetOthersChildren()`).
- **Stints are the only truth for who's on the pitch.** `onField(m, pid) = !!openStint(m, pid)`. `positions` holds nothing but x/y coordinates — never make it authoritative again, and never gate a feature on it.
- **Append-only vs. stateful, and they get different care.** Goals, shots, corners, fouls, possession, and stint records are each written under their own random id — concurrent taps are safe by construction, no work needed. The clock (`periods/{i}/end`) is read-modify-write and is where real races live.
- **`elapsedSec()`/`playedSec()` use `s.end || now` for whichever period is still open.** Closing that period's `end` is what freezes the match's clock math — this is why `endGame()` must close the open period (and, as a polish beyond the strict minimum, every open stint) before setting `ended`. Don't "fix" a drifting-minutes bug anywhere except here.
- **Six flat lookup tables exist because rules cannot iterate.** `access/index/{uid}` answers "may this uid read the club"; `access/teamIndex/{teamId}/{uid}` answers "may this uid change *this* team", and its value is `'coach'`, `'tracker'` or `'helper'` (coach wins, then tracker) because those are not the same permission, and a helper's own powers are checked against `access/teams/{tid}/helpers/{uid}` itself; `access/teamParents/{teamId}/{uid}` answers "is this uid a family on *this* team", and its value is a player id the rule checks against that player's `guardians`, so it can never claim more than the squad does. `access/teamPlayers/{teamId}/{uid}` is the same for a player with her own sign-in (`players/{pid}/self/{uid}`, never `guardians`), and its value is her player id, which is also how the `dm` rule finds her parents. `access/coachIndex/{uid}` answers "is this uid a coach of *any* team", for the training rules, and its value is a team she coaches because that is what her own write of it is checked against; `access/helperIndex/{uid}` is its twin for a team helper (build 117), for the club's drill shelves, and never makes her a coach. All are derived — `syncIndex()`, `syncTeamIndex()`, `syncTeamParents()`, `syncTeamPlayers()` and `syncCoachIndex()` (which keeps helperIndex too) rebuild them from where a uid appears (a parent also adds herself on accepting an invite), and so does the server, the moment a role changes (`functions/access.js`, the same sources and values, never starting a table that is missing); nothing else may write them. Any code that adds or removes a guardian must call `syncTeamParents()` for that team, and a player's own sign-in `syncTeamPlayers()`. `hasAnyRole()` counts `self`, or an admin's phone takes a player out of the index. Another since build 121, on `orgs/` only: `access/teamFans/{teamId}/{uid}`, a player's fan (`squad/{tid}/{pid}/fans/{uid}`, never `guardians` or `self`), valued and checked like `teamPlayers`, kept by `syncTeamFans()` and the server's `accessFansOrgs`; any code that adds or removes a fan calls it, and `hasAnyRole()` counts `fans` too. A seventh since build 182 (DOORS.md, rules version 36): `access/playerIndex/{uid}`, a team she plays on with her own sign-in, checked against `teamPlayers`, kept by `syncPlayerIndex()` (from `syncTeamPlayers()`, her own phone on accepting her invite) and the server beside `teamPlayers`, so a root-level rule (`talk/`) can tell a child's account with one lookup. A rule can only look a path up directly, so the denormalisation is not optional.
- **Practice plans merge on read, and are never replaced wholesale.** They live outside the workspace, at `training/{code}/practices/{teamId}/{eventId}`, keyed by the calendar practice they belong to, which they read day, time, place and length from (`withEntry()`); edits start from `rawPlan()`, so the calendar's fields are never copied into a plan. Deleting the entry never deletes the plan. A plan with no `eid` is from before this and `movePlans()` gives it an entry under its own id; with their own local copy (`sm.train.v1:{club}`) and one listener per team. A plan this phone changed and the club hasn't acknowledged is marked dirty, and a dirty plan is never overwritten by the club's copy; it's re-sent on the first answer after attaching, and on every connect (`flushTraining()`). `schedule/{teamId}/{practiceId}` is no longer written or read; its rule stays until no older app writes it. Templates are the drills' shape: `SHELF.clubTpl`/`SHELF.mineTpl`, same sync, same rules, `normTemplate()` on read.
- **Drills move between shelves by copy, never by link, and a stored diagram is drawn only once it has been rebuilt.** Club drills (`training/{code}/drills`, cached in `train`) and Mine (`userLibrary/{uid}/drills`, cached at `sm.mine.v1:{uid}`) sync like plans: merge on read, a dirty map, one drill per write. Mine is the person's, not the phone's: `forgetMine()` runs whenever the signed-in uid changes, sign-out included, and the app owner's support read (`peekLibrary()`) keeps nothing. Every copy records `from`, and a plan copies a non-built-in drill whole (`drill.card`), so deleting never cascades. Everything read goes through `normDrill()`, which holds lists to `drills.js`'s vocabularies, links to https, and pictures to a built-in drill named by `pic` or to a drawing of her own that `DrillDiagram.clean()` has rebuilt from typed values and `parse()` has passed (`cleanDrawing()`), because any coach can write a club drill and the renderer writes numbers and ids straight into SVG. A club drill's `by`/`byName` are copied onto it when shared and never change, whoever tidies it, so the club still knows who wrote it after she leaves.
- **A rule that needs a node which may not exist yet carries a bridge.** The per-team and per-share rules fall back to the old club-wide behaviour *while their lookup table is missing*, and stop the instant it appears. That is what lets a ruleset be pasted before the app has caught up, on a club that predates the table. Never write a rule that assumes a node the live database might not have — that is the lockout README warns about, and the bridge is how it stops being an ordering problem.
- **Write at the depth the rule sits at.** A rule on `$tid` or `$uid` does not grant its parent, so `pushAll()` writes one team, one match, one member at a time. Pushing a whole collection is refused where pushing each child is fine, and the difference is invisible until a club is locked down and then it is total.
- **Only a club owner takes an admin away** (`access/owners/{uid}`, always an admin too, SECURITY.md, SEC-D8; rules version 13). Admins appoint admins and step down themselves; once a club has an owner the rules sit on each `admins/$uid` (so never write the admin list whole) and refuse an admin taking another admin's `access/index` entry. A club with no owner keeps the old rules (the bridge). Every admin or owner change is logged to `access/log` *before* it is made, so `functions/adminwatch.js` can name who did it when it tells every admin and owner and writes `clubAudit/{code}`; `isClubOwner()` is not `isOwner()` (the app owner, who has no standing in the rules).
- **A child is a person in the club, at `children/{cid}` beside the squad** (AUTH.md, *A child in the club*; rules version 21). Each squad record points at her (`child`) and she lists them (`teams/{tid}: pid`, the rule checking the squad's pointer). Her `guardians` and `self` are copies of each squad record's, valued with the team, which anyone may write and the rule never lets claim more than the squad says; a family named on the child herself is `family/{uid}`, from an invite naming the child. Only her family writes `confirmed`. Registration (`programs`, `waivers`, `regs/{progId}/{cid}`, `agreed/{progId}/{cid}/{wid}_{v}`, and the link at the root, `regOpen/{id}`) is under the club too: only an admin moves a registration past `sent`, only a family agrees to a waiver, an agreement is never changed, and accepting is what lets a child's family into the club. Never put care, contact or medical details on her record: those are care, `care/{cid}` (her family and admins) with a copy per team at `teamCare/{tid}/{pid}` (that team's coaches and admins), kept by `careCopy` and never in a game, squad, backup, push or `public/`. A record made again on every connect (`syncChildren()`) goes straight to the database like a lookup table, never through the outbox; a family's own changes go through the outbox.
- **Roles are derived from where a uid appears** (`access/admins/{uid}`, `access/index/{uid}`, and eventually `orgs/{o}/admins/{uid}` etc.) — never stored as a string on a user. A string role is a second source of truth that goes stale the moment someone changes team.
- **Holding the local copy and drawing it are two different decisions.** The cache exists so a coach with no signal still has her squad, so it is *not* cleared on sign-out — an unsynced game lives only there. But once a club has an admin, a signed-out device must render nothing: no roster, no team, no title row (it carries the club and team names) and no tab bar. The same goes for a phone whose access was withdrawn: a refusal is kept on the phone (`LS_DENIED`) and `copyCheck()` keeps the club shut on an offline reload, clearing it a day on; a copy the club has not confirmed for `OFFLINE_DAYS` is not drawn until it has. Gate on `needsSignIn()` at the top of `render()`, never on the database refusing the read — that answer arrives seconds later, and the names are on screen the whole time. `myTeams()` and `canEditTeam()` must agree with it, via the same `gated()` predicate.
- **A signed-in identity is cached locally (`sm.me`) and cleared on sign-out.** Firebase Auth only restores a session once its module has loaded from the CDN, which does not happen at a field with no signal, so without this a locked-down club shows its lock screen to the coach it belongs to. It is not a permission — the rules decide what a uid may touch. Clearing it on sign-out is what makes signing out bite immediately.
- **The connect-time workspace read merges into local state; it must never replace it wholesale.** A game tracked fully offline exists only in local state until it syncs — a naive `state = snap.val()` at reconnect silently erases it. See `wireBase()` and `mergeConnect()`.
- **Nothing lives only on the phone: every workspace write goes through the outbox.** Firebase keeps an unsent write in memory only, so a page closed with no signal used to lose it. `remoteSet()`/`remoteDel()` record each write at `sm.pending.v1:{club}` until the database acknowledges it; `mergeConnect()` lays what is still owed over the club's copy in the order it was made and `flushPending()` sends it again. A refused write stays, marked, retried on every connect, shown on every screen and in the badge, and is dropped only when the coach says so. `seen` (`sm.seen.v1:{club}`) is what tells a game deleted elsewhere (seen before) from one made here and never sent (not seen, so sent now). Never write to the workspace any other way, and never count something saved until it has left the outbox. The four lookup tables skip it (they are rebuilt every connect). A caller that takes its own change back on a refusal calls `forgetPending()`, as `setRsvp()` does. Plans, drills, Mine and training sessions have their own dirty lists, flushed on every connect by `flushTraining()`, and messages their own outbox; `otherOwed()` folds all but messages into the badge, the banner and the pending sheet, so nothing is called synced while any of it is still only here. Data stores save through `keepStored()`, which says out loud when the phone's storage is full instead of swallowing it. A backup carries the training records under `training`; restoring one writes a training record only where the club, asked first, has nothing.
- **A role entry's value is not always `true`.** One granted by an invite holds the invite id, because that is what the rule checks. Everything that reads a role asks whether the entry is there — keep it that way, never `=== true`.
- **Training sessions merge on read too, and never go inside the club (`orgs/{code}`).** `training/{code}/sessions|booked|came|fees|pay|splans`, with their own local copy (`sm.sess.v1:{club}`) and dirty marks, exactly like practice plans. A booking is `booked/{sid}/{pid}`, never inside the session, because a coach saving the session writes all of it. A family writes only `asked` or `out`, never `in`: a rule can't count spots, so the coach keeps the count. Fees are the one part the rules narrow by reader (admins, that session's coach, that child's family); don't widen a fee read to the club. Deleting a session sends its bookings, register, fees and plan before the session, because those rules find the coach through the session. Fields are `access/org/venues` (`org/venues` on orgs/) and need no rule of their own.
- **A booked slot is a session, its id is its time, and the server books it.** A coach's bookable times are `training/{code}/avail/{bid}`, one date each (a weekly one is a block per week sharing `series`, like practices), 1-1s or a small group, carrying `day0` (the coach's phone's midnight that day, which only a phone in the club's time zone knows). A family never writes a slot's session or booking: her phone asks at `bookAsks/{code}/{uid}/{id}` (`askBooking()`), and the server (`functions/book.js`) checks her child, the coach's and the child's calendars as they stand, and counts the places inside one transaction on `booked/{sid}`, then writes the session at `sessions/k_{coach}_{date}_{HHMM}` and the booking (build 119, rules version 18). A full slot has a waiting list the server works through (`bookFreed`). There are no `seats` and no `slots` list any more (an older block may still carry them; the server reads an older block's `slots` for its start times). Never let a booking or a cancel wait in a queue (it needs a signal), and never write a slot booking from a family's phone any other way.
- **Coaches' time off is read, never obeyed, and never under `access/members`.** `training/{code}/away/{uid}/{id}` (weekly, dates, callout), synced with the training sessions' machinery and read only by coaches' and admins' phones. It enters the app in one place, `busyItems()`: time off is a busy item of hers, and a call-out takes her off that entry's `coaches`. Nothing is cancelled or moved because of it. An admin may write any coach's record (`by` is the admin); `coachStatus()`/`freeCoaches()` answer who can coach at a time. **Club activity (`clubNews()`) is worked out on the phone from what it holds, never sent**: per account and club it keeps what it last saw per source, says nothing on a source's first look or while a source hasn't loaded, and skips whatever `noteMine()` saw this phone write (every write path calls it). A parent hears no club activity, but does get alerts about her own children's calendar (`test/alerts.js`). Field hours and closures are on the field (`access/org/venues/{id}/hours|closed`) and are checked by `fieldShut()`.
- **A phone is in every club its account is in, and My calendar is the person's, private until she says otherwise.** The club on screen is synced in full as always; every other club in `userOrgs` is listened to read-only (`watchMirror()`), cut down by `mirrorSlim()` (her own children only, no stints, no squad) and kept at `sm.mirror.v1:{uid}`, forgotten on sign-out like Mine. Never write to another club from that copy, and never add to it what My calendar doesn't need. `withClub()` swaps `state`/`sess` for its copy synchronously and puts them back, so the club's own calendar code draws it. **Alerts come from the same listening**: messages per club as that club's own inbox would listen (`watchElseMessages()`), and changes to her own calendar in every club (`calAlerts()`), never on a club's first look or a conversation's first read, never what this phone did (`noteMine()`), and not the open club's calendar for an admin (club activity says it); kept at `sm.alerts.v1:{uid}`, forgotten on sign-out. Her busy times at `people/{uid}/busy/{clubTag(code)}` are a date and two times and nothing else, hers alone to read, and the rule refuses them while `set/share` isn't `true`; write the setting first. The server copies them into each club she is in at `training/{code}/elsewhere/{uid}` (her other clubs' only; `functions/mycal.js`), which is what a club's coaches' and admins' phones listen to (`watchBusy()`, never `people/{uid}/busy`). They enter the app in one place, `busyItems()` via `elsewhereOn()`, skipping the open club's own tag.
- **A push token is the person's, and the server is told only what the rules already allow.** `pushTokens/{uid}/{token}` is readable and writable by that account alone, and so is `people/{uid}/mute/{kind}` (`msg`, `notice`, `cal`, `news`; rules version 10): a kind she turned off is never pushed (`messagesFor()` skips her before reading her phones) and never pops up or banners on any phone (`pushAlert()` keeps it, shut, to read; club activity and session news check `muted()` before `ping()`). The phone takes hers down on signing out while she is still signed in (`pushTurnOff()` before `signOut`), gives up a token another account left (`pushCheck()`), and tells `sw.js` who is signed in so a push for anyone else is shown without its words. `functions/push.js` sends each message to exactly the rules' readers, from the lookup tables and held to the squad, never through a bridge clause and never to the author. Every push also leaves her a copy at `people/{uid}/inbox/{id}` (`toInbox()` in `functions/push.js`, rules version 37: hers to read, nobody's to write but the server's), which is how a page open on one club hears her others (`watchInbox()`): notifications are the account's, not the club's on screen. A new kind of push is another trigger there, tested in `test/push.js` for every kind of account; never one that wakes on `orgs/{code}` wholesale, or on a whole game, which a live game writes every few seconds (the calendar's watch a game's `date`, `kickoff` and `called` alone; a followed game's, a goal or a stretch of play created, a goal's `pid`, and `currentHalf` and `ended`). The server's own notes live at `serverState/`, which has no rule, so no phone reads or writes it. Every calendar write carries who made it, `edit: { by, at }`, stamped in `remoteSet()` (`calStamp()`), and a whole entry or game deleted is stamped just before by `remoteDel()` for the team's coaches and admins only, inside a whole entry or game and beside a field written alone; the rules (version 8) refuse a stamp in anyone's name but the writer's, and the server leaves that person out and names her, trusting a stamp only while it is fresh. Never write a calendar change around `remoteSet()`, or it goes out unstamped.
- **Messages never go inside the club either.** `board/{code}/{tid}`, `dm/{code}/{tid}/{familyUid}`, `staffdm/{code}/{a}~{b}` (two colleagues, uids sorted, readable by those two only while both are staff, admins included) and `talk/{code}/{a}~{b}` (build 180, DOORS.md, rules version 34: two people keyed by their accounts and not by a team, a session's coach and a family or an admin and a family, both in the index and at least one of them staff (an admin, a coach, a helper, a session coach), read by the two alone, never an admin (the owner, 2026-10-22; build 182, rules version 36); `cidRoot()` says which root a pair is at, `myTalk()` who may open one, `talkPartners()` who is offered from the sessions, and a player's own sign-in is never in one, on the rule's word from the seventh lookup table, `access/playerIndex/{uid}` (a team she plays on with her own sign-in, checked against `teamPlayers`, kept by `syncPlayerIndex()` and the server beside `teamPlayers`)) sit at the root with rules of their own, because everyone indexed reads the club's teams and games and the connect-time read would carry every family's private conversation onto every phone. A family conversation is readable by that family, that team's coaches and the admins — never one coach alone — and is append-only; either side may start it, and it stays the one thread, so a coach writing first never makes a private line to one parent. `seen/{uid}` and `got/{uid}` are each reader's own markers (read, delivered), written as the later of now and the newest message covered. The lock on screen says who reads a conversation and that it is not end-to-end encrypted; never claim more. A player with her own sign-in reads and writes her parents' conversations (`famThreads()`), and is never a family herself: no thread is keyed by a player.
- **A link for several people is seats, never a counter.** A rule cannot count, so an invite or team link for N people carries `seats/{s1…sN}`; each person writes `seat/{s}` (by her) and then `took/{uid}`, and every grant rule accepts `took/{auth.uid}` wherever it accepts a single-use `used/by` (rules version 20). An invite for several has an `m…` id and is never deleted when one holder's role goes (`forgetInvite()`, `functions/access.js`). A share page or feed with an end date carries `until`, which the `public/` read rule and the calendar function both check.
- **Invite secrets never go inside the club.** Everyone indexed can read its teams, games and access, parents included, so an unspent invite id there is a role anyone in the club can take. The admin's list lives at `clubInvites/{code}`, readable by admins only; the invite itself at `invites/{id}`, readable only by id.
- **The calendar lives under the team, and needs no rule of its own.** Practices and events are `teams/{tid}/events/{eid}`, so the rule on `teams/$tid` decides who changes them (that team's coaches and admins) and the club-wide read decides who sees them. Games stay in `matches` and the calendar reads them; never copy a game into `events`. A weekly practice is one entry per week sharing a `series` id. Do not turn it into a recurrence rule the app expands, because calling off one week has to be one write to one entry. Practice plans hang off these entries.
- **Answers (who is coming) live at `rsvp/{tid}/{g_mid | e_eid}/{pid}`, never inside the game or the entry.** A coach saving a game writes the whole game, so an answer stored inside it is lost to any edit made while a parent was answering; and the rule that lets a parent write grants that one node, so it cannot be stretched to the team or the game. Each answer is stamped with the writer's uid. Answers never go to `public/`, not even as counts.
- **Availability for a game is derived: `isOut()` is the coach's `out[pid]` if she gave one, else the family's answer.** `out[pid] === false` means "playing despite a not going". `toggleout` writes the coach's word only where it differs from the family's, so a changed answer still flows through unless she has decided. Anything that needs who is out calls `isOut()`/`outIds()`, never `Object.keys(m.out)`, which misses the families.
- **The register lives at `teams/{tid}/attend/{eid}/{pid}`, beside the entries, never inside them**, so a practice edit cannot write over it, and keyed by the calendar entry's id so whatever hangs off that entry later (a practice plan's drills) can be counted per player. Games have no register: `cameToGame()` reads minutes and availability. Deleting an entry deletes its register.
- **Only the server writes `public/`** (SECURITY.md, SEC-D11; rules version 19, `.write: false`). Phones make the ids (`teams/{tid}/share`, `calFeed`, a game's `share`) in the club and nothing else; `functions/mirror.js` builds the pages, holding each to the app's `publicDoc()`/`fixtureDoc()`/`calendarDoc()` through `functions/game.js` (the game math ported: change one, change both, `test/mirror.js` fails until you do), and `functions/mycal.js` My calendar's. Whose page is whose is `serverState/pages`; never write `public/` from a phone again.
- **The share link carries only `public: true` entries, and free text bound for `public/` goes through `pubText()`.** A practice is a predictable time and place where children are, and the share link gets forwarded, so team-only is the default. The one place team-only entries reach `public/` is the team's calendar feed (`teams/{tid}/calFeed`), whose id the app shows only to that team's coaches, trackers and the club's admins (one address for everyone cannot be taken back from one family, so families use My calendar's feed, which is theirs alone) and a coach can replace. It carries no players, no numbers and no answers. `test/calendar.js` stringifies the mirror with a name typed into every new free-text field.
- **A game link carries the game's own id (`m.share`), never the season's.** Each game is published alone at `public/{m.share}` with `fixture` set, so whoever a game link reaches (the other team included) cannot get to the season. No id yet means no link, never a fallback to the season id. Rotating the season link replaces every game's too, and deleting a game takes its page down.
- **Never reach for anonymous auth as a shortcut for the public share write hole.** Anonymous uids are per-device: two coaches get two different ids, clearing browser storage locks a coach out of her own share. `AUTH.md` says this explicitly — don't relitigate it.

## Auth/sync races already found and fixed once — don't reintroduce them

- `initSync()` must wait for Firebase Auth's first `onAuthStateChanged` callback (`authReady`) before reading the workspace. A read that races ahead of auth gets denied by a uid-keyed rule even for someone who's signed in a moment later, and that denial used to stick because the read only ever ran once.
- Reattach the workspace read whenever the signed-in uid changes *after* boot too (e.g. someone signs in from the lock screen following an earlier denial) — not only at the very first auth callback.
- `getApp()` must not let two concurrent callers (`initAuth()` and `initSync()`) both call `initializeApp()` — cache the in-flight promise, not just the resolved app, or the second call throws and silently kills whichever init lost the race.
- The retire-club action must check `canAdmin()` inside the click handler itself, not just rely on the button being hidden from non-admins in the render.

## Conventions

- Commit messages: short summary line, blank line, body explaining *why*, not just what. GitHub's history is the changelog; there is no `CHANGELOG.md`.
- Anything a phone does on somebody else's behalf, or that stays true only while some phone is open, gets an entry in `SERVER.md` and a `// SERVER.md:` line on its function; `test/version.js` checks both.
- The app is a static site with a Firebase backend, and **server-side code is allowed**: Cloud Functions on the same Firebase project, in `functions/` (the owner's decision, 2026-10-06; `GOTSPORT.md`, *The server*). The phone stays offline-first: nothing at the sideline may wait on the server, and the outbox, local copies and rules are unchanged. A function writes with admin credentials and so bypasses the rules; every one that acts for a caller checks the caller against the same lookup tables the rules read, and is tested for every kind of account like `rules.js`. Secrets (Stripe, email) live in Secret Manager, never in the repo or `firebase-config.js`. An amount of money never comes from a phone. Webhooks record the event id before the effect.
- Neither the app nor the server ever calls an AI model.
- The calendar feed (`functions/calendar.js`) reads only `public/{id}` and writes nothing, though it runs with admin credentials: the id check is the whole wall, and `test/calfeed.js` pins it. A feed with names in it would be a different function behind a private link, never this one widened. There is no Cloudflare Worker any more; don't bring one back as a second way to do what a function does.
- Children's registration, medical, payment and compliance data never goes inside the club (everyone indexed reads its shared parts); it gets root nodes with rules of their own, as `GOTSPORT.md`, *Protecting the data*, lays out.
- After changing `ics.js`, run `node functions/make.js` so the calendar feed carries the same copy (only `functions/` is uploaded); `test/calfeed.js` fails until you do.
- **The screens' words are picked once, in `GLOSSARY.md`**, and `test/copy.js` holds every screen to it: Players not Squad, Training (the tab) not Practice, Sessions not Training sessions, Club admin not Org admin, short/over not owed, and nothing from the code or the database (Firebase, README, rules, lookup table) on a screen. A refusal is `refusedMsg()`; the detail behind a label is an `INFO` sheet; a role's powers are said once (`roleCard()`), never as a banner. Before adding a label or a toast, check the glossary.
- Comments in this codebase explain reasoning, not just mechanics (see the invariants above for the tone) — keep that up rather than reverting to comments that just restate the line below them.
