# CLAUDE.md

Soccer minutes/substitution tracker, and the team's season calendar. Static site (`app.js`, `index.html`, `styles.css`; `live.js` behind the share pages; `ics.js`, the calendar-file writer both load), Firebase Realtime Database backend, deployed to GitHub Pages. One optional extra: `worker/calendar.mjs`, a read-only Cloudflare Worker that serves calendar feeds from `public/`. Built for a coach tracking subs on a phone at the sideline, often with no signal.

Read `HANDOFF.md` first if it exists and is current. Read `AUTH.md`, `ROADMAP.md`, `SECURITY.md` before touching auth, access, sharing, or the data model — they're design docs, not history, and `AUTH.md` says outright it was "written before any code, because the data model and the rules have to be right first — they are painful to change once twelve teams have data in them." Treat any schema change (`workspaces/{code}` today, `orgs/{orgId}` eventually) as high-stakes, not routine. Read `TRAINING.md` before touching drills, practices or the training data model — same kind of document, written before the code. Built so far: the built-in drill library (`drills.js`), its diagram renderer (`drill-diagram.js`), the Practice tab that reads them, a team's `birthYear`, practice plans (`training/{code}/practices` and `schedule`, with their rules), and the club's and each coach's own drills (`training/{code}/drills`, `userLibrary/{uid}`, with their rules). Templates, and practice plans moving onto the calendar, are not built; `TRAINING-NEXT.md` is the brief for building them. Read `SESSIONS.md` before touching training sessions (1-1s and small groups that belong to no team), fields and permits, session fees or coach hours; same kind of document, written before the code.

## Required after every change to the rules (`database.rules.json`)

- **One ruleset, for every club: `database.rules.json`** (`firebase.json` points the Firebase CLI at it). A database runs one set of rules for every club in it and this site is for any club that turns up, so there is no open "starter" set and no lockdown: a brand-new club is made under the same rules as an established one, through the bootstrap clauses (claim admin and index yourself while the code has neither). Never add a second ruleset; `rules.js` fails if one appears. README explains them and points at them, but never carries a whole copy — a second copy is the one that drifts, and `rules.js` fails if one reappears. Edit the file, never a pasted-back block.
- `node test/rules.js` — evaluates `database.rules.json`, the file you paste, against a mock club, for every kind of account, and walks a brand-new club from nothing to working under the same rules. Exits non-zero on a failed expectation. Rules are the one thing here with no way to try it safely: the only live test is publishing over the real club, and the failure mode README warns about is silent (reads work, every write is refused). Run it before you paste anything into the Firebase console.

## Known gaps are pinned, not hidden

Some behaviour contradicts a design document but is left alone because the fix is a decision rather than a bug — `rules.js` has printed five of those at the end for a while. `test/harness.js` gives that a shape: `knownGap()` asserts what the code does *today*, prints it under `gap` instead of `ok`, and **fails if the behaviour changes in either direction**. Closing a gap is meant to turn a suite red once; the fix is to promote the case to an ordinary `check()` and delete the `knownGap()`, not to widen it.

Pinned today: none. The last one, `wireBase()` replacing local state wholesale on the connect-time read, was closed by the outbox (below) and promoted to ordinary checks in `test/sync.js`. `node test/run.js` lists every gap at the end when there are any.

## Invariants — do not violate these

- **Stints are the only truth for who's on the pitch.** `onField(m, pid) = !!openStint(m, pid)`. `positions` holds nothing but x/y coordinates — never make it authoritative again, and never gate a feature on it.
- **Append-only vs. stateful, and they get different care.** Goals, shots, corners, fouls, possession, and stint records are each written under their own random id — concurrent taps are safe by construction, no work needed. The clock (`periods/{i}/end`) is read-modify-write and is where real races live.
- **`elapsedSec()`/`playedSec()` use `s.end || now` for whichever period is still open.** Closing that period's `end` is what freezes the match's clock math — this is why `endGame()` must close the open period (and, as a polish beyond the strict minimum, every open stint) before setting `ended`. Don't "fix" a drifting-minutes bug anywhere except here.
- **Four flat lookup tables exist because rules cannot iterate.** `access/index/{uid}` answers "may this uid read the club"; `access/teamIndex/{teamId}/{uid}` answers "may this uid change *this* team", and its value is `'coach'` or `'tracker'` because those are not the same permission; `access/teamParents/{teamId}/{uid}` answers "is this uid a family on *this* team", and its value is a player id the rule checks against that player's `guardians`, so it can never claim more than the squad does. `access/coachIndex/{uid}` answers "is this uid a coach of *any* team", for the training rules, and its value is a team she coaches because that is what her own write of it is checked against. All are derived — `syncIndex()`, `syncTeamIndex()`, `syncTeamParents()` and `syncCoachIndex()` rebuild them from where a uid appears (a parent also adds herself on accepting an invite), and nothing else may write them. Any code that adds or removes a guardian must call `syncTeamParents()` for that team. A rule can only look a path up directly, so the denormalisation is not optional.
- **Practice plans merge on read, and are never replaced wholesale.** They live outside the workspace, at `training/{code}/practices/{teamId}/{practiceId}`, with their own local copy (`sm.train.v1:{club}`) and one listener per team. A plan this phone changed and the club hasn't acknowledged is marked dirty, and a dirty plan is never overwritten by the club's copy; it's re-sent on the first answer after attaching, and on every connect (`flushTraining()`). `schedule/{teamId}/{practiceId}` carries when and where only, because the whole club reads it.
- **Drills move between shelves by copy, never by link, and a stored diagram is drawn only once it has been rebuilt.** Club drills (`training/{code}/drills`, cached in `train`) and Mine (`userLibrary/{uid}/drills`, cached at `sm.mine.v1:{uid}`) sync like plans: merge on read, a dirty map, one drill per write. Mine is the person's, not the phone's: `forgetMine()` runs whenever the signed-in uid changes, sign-out included, and the app owner's support read (`peekLibrary()`) keeps nothing. Every copy records `from`, and a plan copies a non-built-in drill whole (`drill.card`), so deleting never cascades. Everything read goes through `normDrill()`, which holds lists to `drills.js`'s vocabularies, links to https, and pictures to a built-in drill named by `pic` or to a drawing of her own that `DrillDiagram.clean()` has rebuilt from typed values and `parse()` has passed (`cleanDrawing()`), because any coach can write a club drill and the renderer writes numbers and ids straight into SVG. A club drill's `by`/`byName` are copied onto it when shared and never change, whoever tidies it, so the club still knows who wrote it after she leaves.
- **A rule that needs a node which may not exist yet carries a bridge.** The per-team and per-share rules fall back to the old club-wide behaviour *while their lookup table is missing*, and stop the instant it appears. That is what lets a ruleset be pasted before the app has caught up, on a club that predates the table. Never write a rule that assumes a node the live database might not have — that is the lockout README warns about, and the bridge is how it stops being an ordering problem.
- **Write at the depth the rule sits at.** A rule on `$tid` or `$uid` does not grant its parent, so `pushAll()` writes one team, one match, one member at a time. Pushing a whole collection is refused where pushing each child is fine, and the difference is invisible until a club is locked down and then it is total.
- **Roles are derived from where a uid appears** (`access/admins/{uid}`, `access/index/{uid}`, and eventually `orgs/{o}/admins/{uid}` etc.) — never stored as a string on a user. A string role is a second source of truth that goes stale the moment someone changes team.
- **Holding the local copy and drawing it are two different decisions.** The cache exists so a coach with no signal still has her squad, so it is *not* cleared on sign-out — an unsynced game lives only there. But once a club has an admin, a signed-out device must render nothing: no roster, no team, and no crumbs, since those carry the club and team names. Gate on `needsSignIn()` at the top of `render()`, never on the database refusing the read — that answer arrives seconds later, and the names are on screen the whole time. `myTeams()` and `canEditTeam()` must agree with it, via the same `gated()` predicate.
- **A signed-in identity is cached locally (`sm.me`) and cleared on sign-out.** Firebase Auth only restores a session once its module has loaded from the CDN, which does not happen at a field with no signal, so without this a locked-down club shows its lock screen to the coach it belongs to. It is not a permission — the rules decide what a uid may touch. Clearing it on sign-out is what makes signing out bite immediately.
- **The connect-time workspace read merges into local state; it must never replace it wholesale.** A game tracked fully offline exists only in local state until it syncs — a naive `state = snap.val()` at reconnect silently erases it. See `wireBase()` and `mergeConnect()`.
- **Nothing lives only on the phone: every workspace write goes through the outbox.** Firebase keeps an unsent write in memory only, so a page closed with no signal used to lose it. `remoteSet()`/`remoteDel()` record each write at `sm.pending.v1:{club}` until the database acknowledges it; `mergeConnect()` lays what is still owed over the club's copy in the order it was made and `flushPending()` sends it again. A refused write stays, marked, retried on every connect, shown on every screen and in the badge, and is dropped only when the coach says so. `seen` (`sm.seen.v1:{club}`) is what tells a game deleted elsewhere (seen before) from one made here and never sent (not seen, so sent now). Never write to the workspace any other way, and never count something saved until it has left the outbox. The four lookup tables skip it (they are rebuilt every connect). A caller that takes its own change back on a refusal calls `forgetPending()`, as `setRsvp()` does. Plans, drills, Mine and training sessions have their own dirty lists, flushed on every connect by `flushTraining()`, and messages their own outbox; `otherOwed()` folds all but messages into the badge, the banner and the pending sheet, so nothing is called synced while any of it is still only here. Data stores save through `keepStored()`, which says out loud when the phone's storage is full instead of swallowing it. A backup carries the training records under `training`; restoring one writes a training record only where the club, asked first, has nothing.
- **A role entry's value is not always `true`.** One granted by an invite holds the invite id, because that is what the rule checks. Everything that reads a role asks whether the entry is there — keep it that way, never `=== true`.
- **Training sessions merge on read too, and never go under `workspaces/{code}`.** `training/{code}/sessions|booked|came|fees|pay|splans`, with their own local copy (`sm.sess.v1:{club}`) and dirty marks, exactly like practice plans. A booking is `booked/{sid}/{pid}`, never inside the session, because a coach saving the session writes all of it. A family writes only `asked` or `out`, never `in`: a rule can't count spots, so the coach keeps the count. Fees are the one part the rules narrow by reader (admins, that session's coach, that child's family); don't widen a fee read to the club. Deleting a session sends its bookings, register, fees and plan before the session, because those rules find the coach through the session. Fields are `access/org/venues` and need no rule of their own.
- **Messages never go under `workspaces/{code}` either.** `board/{code}/{tid}` and `dm/{code}/{tid}/{familyUid}` sit at the root with rules of their own, because everyone indexed reads the whole workspace and the connect-time read would carry every family's private conversation onto every phone. A family conversation is readable by that family, that team's coaches and the admins — never one coach alone — and is append-only.
- **Invite secrets never go under `workspaces/{code}`.** Everyone indexed can read the whole workspace, parents included, so an unspent invite id there is a role anyone in the club can take. The admin's list lives at `clubInvites/{code}`, readable by admins only; the invite itself at `invites/{id}`, readable only by id.
- **The calendar lives under the team, and needs no rule of its own.** Practices and events are `teams/{tid}/events/{eid}`, so the rule on `teams/$tid` decides who changes them (that team's coaches and admins) and the club-wide read decides who sees them. Games stay in `matches` and the calendar reads them; never copy a game into `events`. A weekly practice is one entry per week sharing a `series` id. Do not turn it into a recurrence rule the app expands, because calling off one week has to be one write to one entry. Practice plans hang off these entries.
- **Answers (who is coming) live at `rsvp/{tid}/{g_mid | e_eid}/{pid}`, never inside the game or the entry.** A coach saving a game writes the whole game, so an answer stored inside it is lost to any edit made while a parent was answering; and the rule that lets a parent write grants that one node, so it cannot be stretched to the team or the game. Each answer is stamped with the writer's uid. Answers never go to `public/`, not even as counts.
- **Availability for a game is derived: `isOut()` is the coach's `out[pid]` if she gave one, else the family's answer.** `out[pid] === false` means "playing despite a not going". `toggleout` writes the coach's word only where it differs from the family's, so a changed answer still flows through unless she has decided. Anything that needs who is out calls `isOut()`/`outIds()`, never `Object.keys(m.out)`, which misses the families.
- **The register lives at `teams/{tid}/attend/{eid}/{pid}`, beside the entries, never inside them**, so a practice edit cannot write over it, and keyed by the calendar entry's id so whatever hangs off that entry later (a practice plan's drills) can be counted per player. Games have no register: `cameToGame()` reads minutes and availability. Deleting an entry deletes its register.
- **The share link carries only `public: true` entries, and free text bound for `public/` goes through `pubText()`.** A practice is a predictable time and place where children are, and the share link gets forwarded, so team-only is the default. The one place team-only entries reach `public/` is the team's calendar feed (`teams/{tid}/calFeed`), whose id the app shows only to that team's signed-in members and a coach can replace. It carries no players, no numbers and no answers. `test/calendar.js` stringifies the mirror with a name typed into every new free-text field.
- **A game link carries the game's own id (`m.share`), never the season's.** Each game is published alone at `public/{m.share}` with `fixture` set, so whoever a game link reaches (the other team included) cannot get to the season. No id yet means no link, never a fallback to the season id. Rotating the season link replaces every game's too, and deleting a game takes its page down.
- **Never reach for anonymous auth as a shortcut for the public share write hole.** Anonymous uids are per-device: two coaches get two different ids, clearing browser storage locks a coach out of her own share. `AUTH.md` says this explicitly — don't relitigate it.

## Auth/sync races already found and fixed once — don't reintroduce them

- `initSync()` must wait for Firebase Auth's first `onAuthStateChanged` callback (`authReady`) before reading the workspace. A read that races ahead of auth gets denied by a uid-keyed rule even for someone who's signed in a moment later, and that denial used to stick because the read only ever ran once.
- Reattach the workspace read whenever the signed-in uid changes *after* boot too (e.g. someone signs in from the lock screen following an earlier denial) — not only at the very first auth callback.
- `getApp()` must not let two concurrent callers (`initAuth()` and `initSync()`) both call `initializeApp()` — cache the in-flight promise, not just the resolved app, or the second call throws and silently kills whichever init lost the race.
- The retire-club action must check `canAdmin()` inside the click handler itself, not just rely on the button being hidden from non-admins in the render.

## Current known gaps

- **Joining ships three ways; one door is still missing.** People → *Invite someone* (admins only) makes a single-use, 14-day link for coach, tracker or parent; Squad → **Parents** makes a squad's worth of those at once (admins), or one team link a parent asks through with a shirt number and a coach approves (`joinCodes`, `claims`). README's **Joining a club** has both. Approving is the one place a coach writes `access/index`, with the team id as its value, and only for an approved request to her own team. Not built: coaches making personal invites for their own team, and a "Create a club" door for someone who belongs to nothing — `Setup → Workspace`'s owner-only escape hatch is still how a club is made, so don't remove it.
- **Invites need the three root rule blocks** (`invites`, `clubInvites`, `userOrgs`) published. Without them, making an invite is refused and the app says so. **Messages need two more** (`board`, `dm`), and **team links two more** (`joinCodes`, `claims`), the same way.
- **The drill shelves need the `training` block's `drills` and the `userLibrary` root block published**, like plans: until then a drill saved to Mine or shared with the club stays on the phone and the Drills screen says so. Templates (`templates` in both) have rules and no app yet.
- **Practice plans need the `training` root block and `access/coachIndex` published.** Without them, plans stay on the phone they were made on and the Plans screen says *Saved on this phone only*. Like every rule, they need a signed-in account, so a coach who hasn't signed in keeps her plans on her phone.
- **Messages are not push.** The bell, the toast and the system notification all come from a page that is open; a closed phone hears nothing until the coach uses *Email or share*. Real push needs a server-side sender, which this project does not have — ROADMAP has the shape of it, and it is a decision for the owner, not a quiet addition.
- **This is a client-side gate, not a database one.** `needsSignIn()` stops the app showing a cached club to a signed-out device. It does nothing about who can read the database directly — that is entirely the rules' job, and while the *open* rules are published anyone holding the workspace code can still read everything. The cached copy also remains in localStorage, readable with devtools; signing out makes the app respect it, it does not encrypt it.
- **Three things the rules still do not enforce** — `node test/rules.js` prints them at the end, along with what the current ruleset *did* close. A tracker can write more of a match than the interface offers her (a rule cannot say "a goal and nothing else" without a rule per field); the app owner has no standing in the rules at all, so `isOwner()` opens buttons the database refuses; and claiming a brand-new workspace code is trust-on-first-use. Read that list before treating a refused write as a bug.
- **Calendar sync needs the Worker deployed**, by hand, once per club (README, **Calendar sync**); until `SOCCER_CALENDAR_FEED` is set the calendar offers a copy instead. Google refreshes subscribed calendars on its own slow schedule, whatever the feed asks. Bulk import does not take practices or the new match-day fields yet.
- **Training sessions need six rule blocks under `training/$code`** (`sessions`, `booked`, `came`, `fees`, `pay`, `splans`). Without them a session stays on the phone it was made on, the screen says so, and a family's ask is refused and taken back. Bookings and registers are club-readable at the database, as `rsvp` is; the screen narrows them. `rules.js` prints both of those as deliberate. Not built: packages, two coaches on one session, outside trainers, named pitches.
- **Attendance counts only what has a register.** A past practice nobody took attendance for is reported as untaken, never guessed. Drills a player has done will be the drills on the practice plans of entries she came to, once the training work keys its plans by the calendar entry's id (see `HANDOFF.md`).
- **Parents' answers need the `rsvp` rule block** in a locked-down club; until it is pasted, an answer is refused and taken back off the screen with a message. `rules.js` prints the one thing that rule deliberately does not check (that the item exists).
- **The full `orgs/{orgId}` migration** (`AUTH.md` build order, steps 1–6) hasn't started. `workspaces/{code}` is still the live schema.

## Conventions

- Commit messages: short summary line, blank line, body explaining *why*, not just what — match `CHANGELOG.md`'s existing entries.
- Every shipped change gets a `CHANGELOG.md` entry.
- This stays a static site with a Firebase backend only — no server-side component, and the app itself must never call an AI model. The one exception is `worker/calendar.mjs`, because a calendar subscription cannot be served by static files: it is optional, holds no credentials, writes nothing, and reads only `public/{id}.json`. Keep it that way; anything that would need the Worker to hold a secret or read `workspaces/` is a different project.
- After changing `ics.js`, run `node worker/make.js` so the Worker carries the same copy; `test/worker.js` fails until you do.
- Comments in this codebase explain reasoning, not just mechanics (see the invariants above for the tone) — keep that up rather than reverting to comments that just restate the line below them.
